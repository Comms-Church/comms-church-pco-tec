# Cut a Release — comms-church-pco-tec

This repo already has full release automation on the GitHub side: pushing a tag
`vX.Y.Z` triggers `.github/workflows/release.yml`, which verifies the version,
builds `comms-church-pco-tec.zip`, and publishes a GitHub Release with
auto-generated notes. Installed WordPress sites then pick up the update via
`CCTEC_Updater` (checks the latest release, cached up to 24h; the
"Check for updates" link on the Plugins screen forces it).

So the local job is only: **lint → bump → commit → tag → push → verify.**
Never build or upload a zip manually. Never create the release on github.com.

## Arguments

- No args → patch bump (1.3.0 → 1.3.1)
- `minor` / `major` → bump that part
- An explicit version like `1.4.0` → use it exactly

## Steps

### 1. Preflight

```bash
cd "/Users/addisonroberts/Documents/Plug Ins/comms-church-pco-tec"
git fetch origin
git status --porcelain
git log --oneline origin/main..HEAD   # unpushed commits
git log --oneline "$(git describe --tags --abbrev=0)..HEAD"  # changes since last release
```

- Must be on `main`. If behind `origin/main`, pull first.
- Uncommitted changes are fine — they'll go into the release commit. But show
  the user `git status` output and confirm those changes are all meant to ship.
- If there are **no changes at all** since the last tag (no commits, no dirty
  files), stop and tell the user there's nothing to release.

### 2. Lint — green, or no release

No system PHP is installed. Use the PHP bundled with Local (find it fresh each
time; the version dir changes when Local updates):

```bash
PHP_BIN=$(find "$HOME/Library/Application Support/Local/lightning-services" \
  -type f -name php -path '*darwin-arm64/bin/php' 2>/dev/null | sort -V | tail -1)
for f in comms-church-pco-tec.php includes/*.php; do "$PHP_BIN" -l "$f" || exit 1; done
```

Any syntax error stops the release. If no PHP binary is found, warn the user
and ask whether to proceed unlinted.

### 3. Bump the version — two places, must match the tag

Both live in `comms-church-pco-tec.php` and the workflow hard-fails if either
disagrees with the tag:

1. Plugin header: ` * Version:     X.Y.Z`
2. Constant: `define( 'CCTEC_VERSION',     'X.Y.Z' );`

Read the current version from the header, compute the new one per the bump
argument, and Edit both lines. Preserve the column alignment (spaces after
`Version:` and after the constant name).

### 4. Commit, tag, push

Write a commit message from the actual diff/commits since the last tag, in this
repo's style (see `git log`): `type: summary (vX.Y.Z)` with a body listing the
notable changes. The release notes are auto-generated by GitHub from commits,
so a good message here is the changelog.

```bash
git add -A
git commit -m "..."
git tag "vX.Y.Z"
git push origin main --tags
```

### 5. Verify it went live

The repo is public, so poll unauthenticated (no `gh` CLI installed). Wait for
the Actions run to finish, then confirm the release exists with a zip asset:

```bash
# poll every ~20s, up to ~3 min
curl -s "https://api.github.com/repos/Comms-Church/comms-church-pco-tec/actions/runs?per_page=1" \
  | grep -E '"(status|conclusion)"' | head -2
curl -s "https://api.github.com/repos/Comms-Church/comms-church-pco-tec/releases/latest" \
  | grep -E '"(tag_name|browser_download_url)"'
```

Success = latest release `tag_name` is the new tag AND it has a
`browser_download_url` ending in `comms-church-pco-tec.zip`.

If the run **fails**: fetch the run's `jobs_url` for the failed step name, fix
the cause locally (usually a version/tag mismatch), then either move the tag
(`git tag -f vX.Y.Z && git push -f origin vX.Y.Z`) after an amend, or cut a
fresh patch version — prefer the fresh patch if the bad tag already produced a
public release.

### 6. Report

Tell the user: the new version, the release URL
(`https://github.com/Comms-Church/comms-church-pco-tec/releases/tag/vX.Y.Z`),
and a reminder that WordPress sites will see the update within 24h, or
immediately via "Check for updates" on the Plugins screen.
